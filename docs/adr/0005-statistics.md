# 0005. 통계는 실시간 집계와 명시적 정의로

- 상태: 승인
- 날짜: 2026-09-30

## 배경

원장님이 알고 싶은 것은 "요즘 매출 추이, 잘 되는 메뉴, 신규/단골 비율, 노쇼"다.
이를 어떻게 계산·저장할지, 그리고 "신규 고객", "노쇼율" 같은 말을 정확히 어떻게 정의할지 정해야 했다.

## 결정

1. **별도 통계 테이블 없이 `sale`/`reservation`을 요청 시점에 집계**한다(GROUP BY). 1인 미용실은 연 수천 건 규모이고 `paid_at` 인덱스가 있어 충분히 빠르다. 원본과 통계 테이블이 어긋나는 버그를 원천 차단한다.
2. **`stats/`는 조회 전용.** 엔티티를 새로 만들지 않고, `Repository<Sale, Long>` 마커 인터페이스로 집계 쿼리만 둔다. 쓰기 메서드가 없어 통계 코드가 데이터를 바꿀 수 없다.
3. **날짜 집계는 서울 기준.** 일별/월별 묶음은 `paid_at AT TIME ZONE 'Asia/Seoul'`로 변환한 뒤 묶는다(네이티브 SQL). UTC로 묶으면 자정 근처 매출이 하루 밀린다.
4. **없는 날/달은 0으로 채워** 돌려준다. 일별은 최대 366일, 월별은 항상 12개월.
5. **정의**
   - **신규 고객**: 기간 내 결제한 고객 중 기간 시작 전 결제 이력이 없는 고객. 고객 카드 등록일이 아니라 *실제 첫 결제*가 기준이다.
   - **재방문 고객**: 기간 내 결제했고 기간 시작 전에도 결제한 이력이 있는 고객.
   - 한 기간에 여러 번 와도 1명으로 센다(distinct).
   - **노쇼율** = 노쇼 ÷ (완료 + 노쇼). 예정(`BOOKED`)은 결과가 안 났고, 취소는 미리 알린 것이라 분모에서 제외한다. 분모가 0이면 0.
   - **메뉴별 매출**은 메뉴 id로 묶고 이름은 현재 이름을 보여준다(이름 변경 시 쪼개지지 않도록). 매출 행의 스냅샷 이름 기준이 아니다.
6. 예약 통계는 예약 **시작 시각** 기준으로 기간에 넣는다.

## 검토한 대안

- **사전 집계 테이블(일별 요약 등)**: 조회는 더 빠르지만 정정/취소 시 갱신 누락 버그 위험이 있다. 데이터가 커지면 도입한다.
- **자바에서 전부 조회 후 집계**: 코드는 쉬우나 건수가 늘면 느리고 메모리를 쓴다. DB가 잘하는 일은 DB에 시킨다.
- **신규 고객을 카드 등록일로 정의**: 구현은 쉽지만 미리 카드만 만든 사람이 신규로 잡혀 의미가 왜곡된다.
- **노쇼율 분모를 전체 예약으로**: 미래 예약과 취소가 섞여 비율이 실제보다 낮아 보인다.

## 결과

- 얻는 것: 원본과 항상 일치하는 통계, 단순한 구조, 명확한 지표 정의.
- 감수하는 것: 조회할 때마다 집계 비용이 든다(현 규모에선 무시 가능). 메뉴별 통계는 메뉴 삭제(현재는 판매 중지만 존재)가 생기면 재검토.
- 추후 과제: 요일/시간대별 통계, 기간 비교(전월 대비), 재방문 주기, 단골 순위, 캐시나 사전 집계.
