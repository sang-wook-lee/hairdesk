# 0010. 직원(담당자) 개념을 도입하고 예약 겹침을 직원별로 판단한다

- 상태: 승인 (2번 owner 표시, 6번 담당자 생략 시 주인, 11번 주인 변경은 [ADR 0011](0011-remove-owner-require-staff.md)로 대체됨)
- 날짜: 2026-11-20

## 배경

지금까지 hairdesk는 "1인 미용실"을 전제로 했다. 그래서 예약·매출에 "누가 시술했는가"가 없고,
예약 겹침도 "전체 예약 중 시간이 겹치면 거부"(ADR 0003)로 만들었다.

고객 상세 화면에 방문 이력, **최근 시술 담당**, 담당자별 이력을 보여주려면 담당자가 데이터로 존재해야 한다.
직원이 둘 이상인 매장도 쓸 수 있게 하려면 겹침 규칙도 직원별로 바뀌어야 한다.

## 결정

1. **`staff` 테이블을 새로 만든다.**

   | 컬럼 | 타입 | 설명 |
   |---|---|---|
   | `id` | BIGINT 자동 증가 | 기본 키 |
   | `name` | VARCHAR(30) NOT NULL | 이름 (예: 김하나, 이지수) |
   | `position` | VARCHAR(30) NOT NULL | 직책. 자유 입력, 필수 (예: 원장, 실장, 디자이너, 인턴) |
   | `owner` | BOOLEAN NOT NULL DEFAULT FALSE | 매장 주인(기본 담당자) 표시. **정확히 1명만 true** |
   | `active` | BOOLEAN NOT NULL DEFAULT TRUE | 근무 중 여부 |
   | `created_at`, `updated_at` | TIMESTAMPTZ NOT NULL | 다른 테이블과 동일 |

2. **`owner`(매장 주인)와 `position`(직책)은 별개다.** 매장 주인은 정확히 1명이지만, "원장" 직책은 여러 명일 수 있다.
   주인이 직책 "원장"이 아닐 수도 있고, 직책이 원장인 사람이 주인이 아닐 수도 있다.
   "주인은 정확히 1명"은 DB가 보장한다. `owner = TRUE`인 행에만 거는 부분 유니크 인덱스를 쓴다.
   `CREATE UNIQUE INDEX uk_staff_owner ON staff (owner) WHERE owner`
   주인은 비활성화할 수 없다(서비스에서 409). `owner`는 "담당자를 생략했을 때 누구인가"를 정하는 데만 쓴다.
3. **직원은 삭제하지 않고 비활성화한다.** 시술 메뉴의 판매 중지와 같은 방식이다. 비활성 직원에게는 새 예약을 잡을 수 없지만,
   과거 예약·매출에는 그대로 남는다.
4. **`reservation.staff_id`, `sale.staff_id`를 추가한다. (NOT NULL, `staff` 참조)**
   - 예약 결제로 만든 매출의 담당자는 예약의 담당자를 따른다.
   - 워크인 매출(예약 없음)은 담당자를 따로 받으므로 `sale`에도 컬럼이 필요하다.
5. **직원 이름은 매출에 복사(스냅샷)하지 않고 연결만 한다.** 메뉴 가격은 바뀌면 과거 장부가 틀어지지만,
   직원 이름 변경은 오타 정정이나 개명이라 과거 기록도 새 이름으로 보이는 것이 맞다. (ADR 0004의 스냅샷과 다른 판단)
6. **예약 요청의 `staffId`는 생략할 수 있다. 생략하면 매장 주인(`owner = true`)으로 처리한다.**
   기존 앱이 `staffId` 없이 예약을 보내도 계속 동작한다.
   매출 등록에서 예약 결제는 예약의 담당자를 쓰고, 워크인은 생략 시 매장 주인이다.
7. **예약 겹침 규칙을 "같은 직원끼리만"으로 바꾼다.** ADR 0003의 DB 제약을 교체한다.

   ```sql
   -- 이전: 전체 예약 중 시간 겹침 금지
   EXCLUDE USING gist (tstzrange(start_at, end_at) WITH &&) WHERE (status IN ('BOOKED','COMPLETED'))
   -- 이후: 같은 직원의 시간 겹침 금지
   EXCLUDE USING gist (staff_id WITH =, tstzrange(start_at, end_at) WITH &&) WHERE (status IN ('BOOKED','COMPLETED'))
   ```

   `btree_gist` 확장은 V1에서 이미 켜져 있다. 서비스의 사전 확인도 직원별로 바꾼다. DB 제약이 최종 방어선인 구조는 그대로다.
8. **같은 고객이 같은 시간에 여러 직원에게 예약하는 것은 허용한다.** 어머니와 자녀가 함께 와서 각자 다른 디자이너에게
   받는 가족 손님이 있기 때문이다. 겹침을 막는 기준은 "같은 직원"뿐이고 고객은 기준이 아니다.
   (한 사람이 같은 직원에게 겹치게 예약하는 것은 위 7번 규칙으로 막힌다.) 이 규칙은 테스트로 고정한다.
9. **기존 데이터는 마이그레이션(V6)에서 채운다.** 이름 `원장`, 직책 `원장`, `owner = true`인 직원 1명을 만들고,
   기존 예약·매출의 `staff_id`를 모두 그 직원으로 채운 뒤 NOT NULL로 바꾼다. 이름과 직책은 앱에서 수정할 수 있다.

10. **직원은 직원 번호(= `id`)로 구분한다. 이름·직책이 같아도 등록할 수 있다.** 동명이인에 직책까지 같을 수 있으므로
    (이름, 직책)에 유니크 제약을 걸지 않는다. 화면에는 "김하나 (#3)"처럼 번호를 함께 보여 구별한다.
    번호는 자동 증가 `id`를 그대로 쓰며, 사람이 따로 정하는 사번 컬럼은 두지 않는다.
11. **매장 주인은 바꿀 수 있다.** `POST /api/staff/{id}/make-owner`가 한 트랜잭션에서 기존 주인의 표시를 끄고
    대상의 표시를 켠다. 대상은 근무 중(`active`)이어야 한다. 새 직원을 등록할 때는 항상 `owner = false`다.
    부분 유니크 인덱스 때문에, 표시를 끄는 UPDATE가 켜는 UPDATE보다 먼저 DB에 반영되어야 한다.

## 검토한 대안

- **직원 없이 `reservation.staff_name` 문자열만 추가**: 컬럼 하나로 끝나지만 오타로 같은 사람이 여럿 생기고, 직원별 겹침 판단과 통계가 불가능하다.
- **`staffId` 필수로 받기**: 규칙이 가장 단순하지만 앱의 예약 폼을 고치기 전까지 예약 등록이 깨진다. 개발 중이라 감수할 수도 있었다.
- **"id가 가장 작은 직원 = 기본 담당자"로 판단**: 컬럼이 늘지 않지만 그 사실이 코드 어디에도 드러나지 않고 순서에 숨는다.
- **`owner` 없이 직책 "원장"으로 기본 담당자 판단**: 원장이 여러 명일 수 있어 "생략하면 누구인가"가 정해지지 않는다.
- **직책을 고정 목록(enum)으로**: 오타 없이 직책별 집계가 가능하지만 매장마다 다른 호칭을 쓰려면 코드와 DB 제약을 고쳐야 한다.
- **직책을 선택 입력으로**: 등록은 편하지만 직책 없는 직원이 생겨 화면 표시가 들쭉날쭉해진다.
- **같은 고객의 동시간대 예약 금지**: 한 사람이 두 곳에 있을 수 없다는 점에서는 자연스럽지만, 가족 손님(어머니와 자녀가 같은 시간에 각각 예약)을 막는다.
- **직원 이름 스냅샷**: 개명 후에도 당시 이름이 남지만 컬럼이 늘고, 같은 사람의 기록이 이름별로 갈라진다.

## 결과

- 얻는 것: 방문 이력과 "최근 시술 담당"을 보여줄 수 있다. 직원이 늘어도 겹침 규칙이 올바르게 동작한다. 기존 앱과 데이터가 그대로 동작한다.
- 감수하는 것: "생략하면 매장 주인"이라는 기본값 규칙이 API에 생긴다.
  같은 고객이 같은 시간에 여러 직원과 잡히는 것은 가족 손님을 위해 허용하므로, 실수로 이중 예약해도 서버가 막지 못한다.
  (화면에서 경고를 띄울지는 앱 단계에서 다시 정한다.)
- 직책은 자유 입력이라 표기가 흔들릴 수 있다(원장/원장님). 직책별 통계를 만들게 되면 그때 정리 방식을 다시 정한다.
- 이번에 하지 않는 것: 직원별 매출 통계, 직원별 휴무·영업시간, 직원 로그인과 권한(인증은 P3).
- 이후 작업: 직원 API → 예약·매출 연결과 겹침 제약 교체 → 샘플 데이터 → 앱 화면.
  마이그레이션은 둘로 나눈다. V6은 `staff` 테이블과 기본 직원, V7은 예약·매출의 `staff_id`와 겹침 제약 교체다.
  (결정 9번의 기존 데이터 채우기는 V7에서 한다.)
- 같은 이름·직책이 허용되므로, 직원 이름만 보고 담당자를 판단하는 화면은 만들지 않는다. 항상 번호와 함께 보여준다.
  이 ADR이 승인되면 ADR 0003에 "겹침 규칙은 0010에서 직원별로 바뀜"을 덧붙인다.
