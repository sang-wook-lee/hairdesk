# 0001. 기술 스택 선택

- 상태: 승인
- 날짜: 2026-09-29

## 배경

1인 미용사용 예약·고객·매출 관리 서비스를 만든다. 목표는 세 가지다.

1. 백엔드 개발자 재취업용 포트폴리오
2. AI 도구 없이도 혼자 유지보수 가능할 것
3. 가능하면 실제 출시

선택 기준: **① 기존 경력과의 연속성**, **② 국내 백엔드 채용 시장**, **③ 예약 도메인 적합성**.

개발자 배경: Java + Spring Boot + Oracle (SI 2년, 배달 플랫폼 백엔드 2년).

## 결정

| 영역 | 선택 |
|---|---|
| 언어 | Java 21 (LTS) |
| 프레임워크 | Spring Boot (생성 시점의 최신 안정 버전) |
| 영속성 | Spring Data JPA (+ 복잡한 통계 쿼리는 QueryDSL 또는 네이티브 SQL) |
| DB | PostgreSQL |
| 스키마 관리 | Flyway |
| 빌드 | Gradle (Groovy DSL) |
| 테스트 | JUnit 5, Testcontainers(실제 PostgreSQL로 통합 테스트) |
| API 문서 | springdoc-openapi (Swagger UI) |
| 실행 환경 | Docker Compose |
| 클라이언트 | Flutter (백엔드 이후) |

## 검토한 대안

### 언어: Kotlin
- 장점: 간결한 문법, null 안정성.
- 채택 안 함: 학습 비용이 생기고, 국내 공고에서 필수 조건인 곳은 아직 소수다. "AI 없이 유지보수"하려면 가장 익숙한 언어가 유리하다.

### 영속성: MyBatis
- 장점: 기존 SI 경험과 일치, SQL을 직접 제어.
- 채택 안 함: 국내 서비스 회사 공고는 JPA가 사실상 기본이다. 예약·정액권처럼 상태가 바뀌는 도메인 로직은 엔티티에 담는 편이 자연스럽다.
- 단, JPA로 표현이 어색한 통계 쿼리는 억지로 JPA로 풀지 않는다.

### DB: Oracle
- 장점: 가장 익숙함.
- 채택 안 함: 무료판(XE)은 리소스 제한이 있고, 상용 라이선스와 클라우드 비용이 개인 프로젝트에 맞지 않는다. 채용 시장에서도 SI·금융 쪽에 치우쳐 있다.

### DB: MySQL
- 장점: 국내 서비스 회사에서 가장 많이 쓴다(공고 수 기준 우세).
- 채택 안 함: 아래 PostgreSQL의 도메인 적합성이 더 크다고 판단했다. SQL·JPA 경험은 DB 간 대부분 이전 가능하다.

### PostgreSQL을 고른 결정적 이유
1. **이중 예약 방지를 DB 제약조건으로 강제할 수 있다.**
   범위 타입(`tstzrange`) + `EXCLUDE USING gist` 제약으로 "같은 디자이너의 예약 시간은 겹칠 수 없다"를 DB 수준에서 보장한다. 동시 요청이 들어와도 애플리케이션 락 없이 막힌다.
2. **DDL도 트랜잭션 안에서 실행된다.** Flyway 마이그레이션이 중간에 실패하면 깔끔하게 롤백된다. (MySQL은 DDL 실행 시 암묵적 커밋)
3. **Oracle과 개념이 가깝다.** 시퀀스, PL/pgSQL, MVCC 등. 경력의 연속성이 있다.
4. 무료이고, 클라우드 무료 티어 선택지가 많다.

### 빌드: Maven
- 채택 안 함: 국내 서비스 회사는 Gradle이 더 일반적이다. Kotlin DSL 대신 Groovy DSL을 쓰는 이유는 Kotlin 문법 없이 읽을 수 있고, 참고 자료가 가장 많기 때문이다.

## 결과

- 얻는 것: 경력을 살리면서 채용 시장의 표준 스택을 보여줄 수 있다. "동시성 문제를 DB 제약으로 해결했다"는 구체적인 면접 사례가 생긴다.
- 감수하는 것: PostgreSQL 고유 기능(`EXCLUDE` 제약 등)을 쓰면 다른 DB로 옮기기 어려워진다. → 이식성보다 데이터 무결성을 우선한다.
- 로컬 개발에 Docker가 필요하다.
