# 0002. 고객 식별 방식과 개인정보 최소 수집

- 상태: 승인
- 날짜: 2026-09-30

## 배경

고객 카드를 만들면서 두 가지를 정해야 했다.

1. 같은 고객이 중복 등록되는 것을 어떻게 막을까?
2. 개인정보를 어디까지 받고, 어떻게 보여줄까?

현장 사정: 미용실에서는 부모 번호로 아이를 예약하는 등 **한 번호를 가족이 같이 쓰는 경우**가 흔하다.
고객을 찾을 때는 **"뒷번호 5678"** 처럼 번호 뒷자리로 찾는 경우가 많다.

## 결정

1. **(이름, 휴대폰 번호) 조합에 UNIQUE 제약.** 번호 단독 UNIQUE는 쓰지 않는다.
2. **번호는 숫자만 저장** (`010-1234-5678` → `01012345678`). 입력 형식은 자유롭게 받고, 엔티티가 정규화한다.
   DB에도 CHECK 제약(`^01[016789][0-9]{7,8}$`)을 둬서 다른 경로로 들어온 잘못된 값도 막는다.
3. **검색**: 키워드가 이름에 포함되거나, 키워드의 숫자 부분이 번호에 포함되면 찾는다.
4. **최소 수집**: 이름, 번호, 성별(선택), 메모, 문자 수신 동의만 받는다. 생년월일·주소는 받지 않는다.
5. **문자 수신 동의(`sms_consent`)는 기본값 false.** 홍보 문자는 동의한 고객에게만 보낸다(정보통신망법).

## 검토한 대안

- **번호 단독 UNIQUE**: 가장 단순하지만 가족 고객을 등록할 수 없어 현장과 맞지 않는다.
- **제약 없음 + 화면에서 경고만**: 유연하지만 동시 요청이나 실수로 같은 사람이 중복 등록된다.
- **번호 마스킹(010-****-5678)을 API 응답에 적용**: 원장 본인은 전화를 걸어야 하므로 전체 번호가 필요하다.
  → 직원 계정/권한이 생기는 시점(인증 기능)에 역할별 마스킹을 다시 검토한다.

## 결과

- 얻는 것: 현장 사용 방식에 맞는 식별 규칙. 중복 방지를 DB 제약으로 보장한다.
- 감수하는 것: 같은 번호에 동명이인 가족이 있으면 등록할 수 없다(매우 드문 경우, 이름에 구분자를 붙여 우회).
- `phone LIKE '%5678'` 검색은 일반 인덱스를 타지 못한다. 1인 미용실 규모(수천 명)에선 문제없고,
  데이터가 커지면 뒷 4자리 컬럼이나 pg_trgm 인덱스를 검토한다.
- 추후 과제: 고객 삭제 요청 시 개인정보 파기(익명화) 정책. 매출 기록과의 관계를 정한 뒤 결정한다.
