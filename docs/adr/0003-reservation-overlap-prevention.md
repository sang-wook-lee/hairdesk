# 0003. 예약 시간 겹침 방지는 DB 제약으로

- 상태: 승인 (겹침 기준은 [ADR 0010](0010-staff.md)에서 "같은 직원끼리만"으로 바뀜)
- 날짜: 2026-09-30

## 배경

1인 미용사는 한 번에 한 명만 받는다. 겹치는 시간의 예약은 절대 생기면 안 된다.
"서비스에서 겹치는 예약이 있는지 조회 → 없으면 저장" 방식은 **거의 동시에 들어온 두 요청이 둘 다 조회를 통과**할 수 있다(경쟁 상태).

## 결정

1. **PostgreSQL EXCLUDE 제약**으로 겹침을 막는다. (`tstzrange(start_at, end_at) WITH &&`, `btree_gist` 확장 — V1)
2. 서비스에서도 저장 전에 겹침을 먼저 조회해 **친절한 409 메시지**를 준다. DB 제약은 최종 방어선이다.
3. 시간 구간은 `[시작, 종료)`. 종료 시각과 같은 시각에 시작하는 예약은 허용한다.
4. 자리를 차지하는 상태는 `BOOKED`, `COMPLETED`. `CANCELLED`, `NO_SHOW`는 제약에서 제외해 같은 시간에 다시 예약할 수 있다.
5. `end_at`은 저장한다(시작 + 메뉴 소요시간). 메뉴 소요시간이 나중에 바뀌어도 과거·확정 예약은 변하지 않는다.
6. 취소·완료·노쇼는 `BOOKED`에서만 가능하다. 시간 변경도 `BOOKED`에서만 가능하다. 취소한 예약을 되살리지 않고 새로 등록한다.

## 검토한 대안

- **서비스 조회만**: 가장 쉽지만 동시 요청에 뚫린다.
- **DB 락(SELECT FOR UPDATE, 어드바이저 락)**: 가능하지만 코드가 복잡해지고, 다른 경로(SQL 직접 수정)는 못 막는다.
- **UNIQUE(start_at)**: 시작 시각이 정확히 같을 때만 막아서 30분 겹침 등을 못 잡는다.

## 결과

- 얻는 것: 어떤 경로로도 겹치는 예약이 저장되지 않는다는 보장.
- 감수하는 것: 디자이너가 여러 명이 되면 제약에 `designer_id WITH =`를 추가하는 마이그레이션이 필요하다(btree_gist는 이미 켜져 있음).
  → **반영됨(2026-11-20)**: V7에서 제약을 `staff_id WITH =, 시간 구간 WITH &&`로 교체했다. 이 문서의 "겹치면 안 된다"는 "같은 직원의 예약끼리"로 읽는다. 자세한 결정은 ADR 0010.
- 제약 위반은 `DataIntegrityViolationException`으로 올라오며 `GlobalExceptionHandler`가 409로 바꾼다.
