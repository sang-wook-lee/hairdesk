# 0004. 매출은 스냅샷을 가진 장부로 기록한다

- 상태: 승인
- 날짜: 2026-09-30

## 배경

예약이 완료되면 "얼마를 어떻게 받았는가"를 기록해야 한다. 정할 것이 여럿 있었다.

- 메뉴 가격은 나중에 바뀐다. 과거 매출은 바뀌면 안 된다.
- 예약 없이 오는 손님(워크인)도 매출이 생긴다.
- 같은 예약에 결제가 두 번 기록되면 안 된다.
- 돈을 어떤 타입으로 다룰 것인가.

## 결정

1. **예약과 별개의 `sale` 테이블.** 예약은 "오기로 한 것", 매출은 "받은 것"이다. 취소·노쇼 예약에는 매출이 없고, 워크인 매출은 예약이 없다.
2. **스냅샷 저장**: 결제 시점의 `menu_name`, `price`(정가)를 매출 행에 복사한다. 실제 받은 금액은 `amount`. 할인액은 `price - amount`로 계산한다(별도 컬럼 없음, 중복 저장으로 인한 불일치를 피한다).
3. **금액은 `int`(원)**, 합계는 `long`. 원화는 소수가 없고, 메뉴 가격 타입과 일관된다.
4. **"결제 = 시술 완료"**: 예약으로 매출을 등록하면 `BOOKED`는 자동으로 `COMPLETED`가 된다(한 트랜잭션). 이미 `COMPLETED`는 그대로, `CANCELLED`/`NO_SHOW`는 409.
5. **이중 결제 방지는 `UNIQUE(reservation_id)`** (ADR 0003과 같은 방식: 서비스가 먼저 확인해 친절한 메시지, DB가 최종 방어). 워크인은 `reservation_id`가 NULL이며 PostgreSQL UNIQUE는 NULL끼리 충돌하지 않으므로 여러 건 가능하다.
6. **삭제 API 없음, 정정만.** 수정 가능한 것은 금액·결제수단·결제시각·메모. 고객·메뉴·정가는 바꾸지 않는다.
7. **매출 날짜는 `paid_at`** (서울 기준 날짜로 집계). 기간 조회 규칙은 예약과 동일하며 `SeoulDates`로 공통화했다.

## 검토한 대안

- **예약 테이블에 금액 컬럼 추가**: 테이블이 하나라 단순하지만 워크인을 표현할 수 없고, 예약 취소 후 재예약 같은 이력과 섞인다.
- **메뉴만 참조하고 가격은 조회 시 메뉴에서 읽기**: 가격을 올리면 과거 매출 통계가 소급 변경된다.
- **`BigDecimal`**: 소수 금액이 필요 없어 과하다. 외화나 세금 계산이 생기면 재검토.
- **결제와 완료 처리를 별도 단계로 강제**: 정합성은 명확하지만 원장님이 매번 두 번 눌러야 한다.
- **매출 삭제 허용**: 입력 실수를 지우기 쉽지만 장부의 신뢰를 잃는다. 정정으로 충분하다.

## 결과

- 얻는 것: 과거 매출이 가격 변경에 영향받지 않는다. 이중 결제가 DB 수준에서 불가능하다. 결제 한 번으로 예약 상태까지 정리된다.
- 감수하는 것: 매출 정정 이력(누가 언제 무엇을 바꿨는지)은 남지 않는다. 환불/결제 취소도 아직 없다.
- 추후 과제: 환불(마이너스 매출 또는 취소 상태), 정정 이력, 부분 결제/선결제, 통계(`stats/`)에서 이 요약 쿼리를 확장.
