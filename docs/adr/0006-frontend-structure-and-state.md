# 0006. 프론트엔드 구조와 상태 관리: 기능별 폴더 + setState + 생성자 주입

- 상태: 승인
- 날짜: 2026-10-23

## 배경

Flutter 앱(`app/`)을 만들기 시작하면서 폴더 구조와 상태 관리 방식을 정해야 했다.
프로젝트 원칙은 "개발자가 AI 없이도 이해하고 유지보수할 수 있어야 한다"이고, 개발자는 Flutter/Dart가 처음이다.
화면은 메뉴 → 예약 → 결제 → 고객 → 통계 순으로 하나씩 늘려 간다.

## 결정

1. **기능(feature) 단위 폴더**: `lib/features/menu/`, `lib/features/reservation/` …
   백엔드가 도메인별 패키지(`menu/`, `reservation/`)인 것과 대응시켜, 한 기능을 고칠 때 한 폴더만 보면 되게 한다.
   공통 코드(API 클라이언트, 포맷터)는 `lib/core/`.
2. **계층은 3개로 제한**: 모델(`menu.dart`) / 저장소(`menu_repository.dart`, 서버 호출) / 화면(`*_page.dart`).
   화면은 HTTP나 API 주소를 모르고, 저장소만 부른다.
3. **상태 관리는 Flutter 기본 기능만 사용**: `StatefulWidget` + `setState` + `FutureBuilder`. 외부 상태 관리 라이브러리는 아직 쓰지 않는다.
4. **의존성은 생성자로 전달**한다(`MenuListPage(repository: ...)`). 앱 시작점(`main.dart`)에서 한 번 조립한다.
   전역 변수나 서비스 로케이터(마법처럼 어디서든 꺼내 쓰는 방식)는 쓰지 않는다. 테스트에서는 가짜 저장소를 넣는다.
5. **모델은 손으로 쓴다**: `fromJson`/`toJson`을 직접 작성한다. 코드 생성(json_serializable, freezed)은 쓰지 않는다.
6. **한글 응답은 `utf8.decode(bodyBytes)`로 읽는다** (`ApiClient`에 한 곳으로 모음).

## 검토한 대안

- **Riverpod / Bloc / Provider**: 여러 화면이 같은 상태를 공유할 때 강력하지만, 지금은 화면이 독립적이라 개념만 늘어난다.
  *도입 신호*: ① 두 화면 이상이 같은 데이터를 보여주고 한쪽 변경이 다른 쪽에 즉시 반영돼야 할 때(예: 예약 화면에서 결제하면 오늘 일정과 매출 요약이 같이 갱신),
  ② 화면 간에 `repository`를 3단계 이상 넘겨주는 코드가 불편해질 때. 그때 새 ADR로 결정한다.
- **json_serializable / freezed 코드 생성**: 보일러플레이트가 줄지만 생성 코드가 생겨 "AI 없이 이해"하기 어려워진다.
- **layer 단위 폴더**(`models/`, `pages/`, `repositories/`): 작은 앱엔 단순하지만 기능이 늘면 한 기능을 보려고 폴더 세 곳을 오가야 한다.

## 결과

- 얻는 것: 읽는 데 필요한 개념이 최소(위젯, setState, Future). 화면 로직을 가짜 저장소로 빠르게 테스트할 수 있다.
- 감수하는 것: 화면 간 상태 공유가 필요해지면 코드를 옮겨야 한다. `setState` 기반 코드는 규모가 커지면 장황해진다.
