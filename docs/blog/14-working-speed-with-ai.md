AI가 코드를 빨리 쓰는 건 장점이다. 그런데 이번에는 빠르다는 것 자체가 문제였다. 내가 이해하기도 전에 코드가 쌓였기 때문이다.

---

## 한 장 요약 (복기용)

| 항목 | 내용 |
|---|---|
| 문제 | AI가 설계를 보여주기 전에 구현부터 했다. "너무 빠르다"고 느꼈다 |
| 바꾼 방식 | 설계 설명 → 선택지 → 작은 단위로 멈추고 확인 → 내가 승인하면 커밋 |
| 효과 | 설계 오류를 코드가 쌓이기 전에 잡았다 (오너 삭제, 챕터 11) |
| AI의 실수 | 이 기간에 인정한 실수가 적어도 일곱 가지 |
| 또 다른 문제 | 세션이 바뀌면 AI가 이전 대화를 기억하지 못한다 → 기록이 기억을 대신해야 한다 |

---

## 1. 어떤 상황이었나

챕터 1의 4절에 "무엇을 어떻게 만들지는 내가 정한다"고 적었다. 그런데 실제로는 그렇게 되지 않던 순간이 있었다.
고객 관리 화면을 하자고 했더니 AI가 백엔드부터 한꺼번에 만들기 시작했고, 어떤 컬럼을 추가하는지, 어떤 규칙을 정하는지 내가 보기 전에 코드가 먼저 나왔다.

## 2. 내가 한 말

그때 이렇게 말했다. [직접 확인]

> 그러니까 작업 전에 어떤 도메인, 컬럼을 추가할 건지 설계를 먼저 보여줬어야지.

그리고 이전부터 느끼던 것도 말했다.

> 지금까지는 너무 빨랐다고 느껴. 작은 단위의 작업도 내게 선택권을 주고, 왜 이 작업을 하는지 설명하면서 진행해줘.

## 3. 바뀐 작업 방식

이 뒤로 작업은 이런 순서가 됐다.

1. **설계를 먼저 보여준다.** 코드 없이 글로, 어떤 컬럼과 API를 만드는지, 왜인지.
2. **선택지를 준다.** 그냥 "이렇게 하겠습니다"가 아니라 "A, B, C 중 무엇이 좋나요"로 묻는다.
3. **작은 단위로 만들고 멈춘다.** 저장소 → 서비스 → 컨트롤러 → 테스트를 한 번에 하지 않고, 층마다 보여주고 확인받는다.
4. **내가 승인하면 커밋한다.** 푸시는 따로 물어본다.

속도는 느려졌다. 대신 이해한 채로 따라갈 수 있게 됐다. 이건 `CLAUDE.md`의 첫 원칙("AI 없이도 이해하고 유지보수")을 실제 일하는 방식으로 옮긴 것이다.

## 4. 느려진 덕에 잡은 설계 오류

이 방식이 효과를 본 가장 큰 사례가 챕터 11의 오너 삭제다. 선택지 중에서 내가 "owner 표시 칸"을 골랐는데, 직원 화면을 설계하는 단계에서 이상함이 드러났다. 코드가 훨씬 많이 쌓인 뒤였다면 지우기가 더 어려웠을 것이다.
승인한 설계가 틀렸어도 괜찮았던 이유는, 작은 단위로 가고 있어서 되돌릴 비용이 작았기 때문이다.

AI가 낸 안에 내가 이유를 물은 일도 있다. 같은 요청을 두 번 보내도 그냥 성공으로 처리하자는 안에 "왜 그걸 권하느냐"고 물었고, AI가 이유를 설명한 뒤에 내가 골랐다. 설명을 들어도 납득이 안 되면 그냥 넘어가지 않았다.

## 5. AI의 실수들

같은 기간에 AI가 낸 실수도 있었다. 숨기지 않고 적어 둔다.

- **설계를 안 보여주고 구현을 시작했다.** 위의 일.
- **쓰다 만 초안 코드가 스크립트에 섞여 들어갔다.** 발견해서 버렸다.
- **존재하지 않는 고객 번호로 서버를 확인했다.** 확인 요청부터 잘못 만들어서, 의미 없는 결과가 나왔다.
- **테스트 개수를 틀리게 셌다.** 8개를 7개로, 11개를 10개로.
- **변경 스크립트의 줄바꿈 오류로 첫 확인이 전부 무효였다.** (챕터 12)
- **문서 표의 칸을 어긋나게 고쳤다.** PROGRESS.md 타임라인 줄을 이어 붙이다가 커밋 수 칸에 설명이 들어갔다. 바로 고쳤다.
- **글에 사실과 다른 문장을 썼다.** 이 시리즈 초안의 문장 하나가 실제 일과 달랐고, 쓴 글을 사실과 대조하다가 발견해서 고쳤다.

공통점은 **확인하면 잡히는 실수**라는 것이다. AI가 틀리는 걸 막을 수는 없으니, 틀려도 잡히는 구조(작은 단위, 테스트, 사실 대조)를 만드는 쪽이 현실적이다.

## 6. 세션이 바뀌면 기억이 사라진다

더 답답했던 건 속도가 아니라 **기억**이었다. AI는 대화(세션)가 바뀌면 이전에 한 이야기를 기억하지 못한다.

- 이전 세션에서는 개발 환경(Docker)을 알아서 켜 줬는데, 새 세션에서는 "켜 주세요"라고 물었다. 내가 이렇게 말했다. [직접 확인]
  > 이전 세션에서는 개발 환경을 알아서 세팅해줬는데 왜 지금은 내가 켜야 돼?
- 블로그를 어디에 올리는지, 저장소가 공개인지 같은 것도 새 세션에서는 다시 물어봐야 했다.
  > 너랑 같이 한 작업인데 세션마다 기억이 다르니 너무 불편하다. 세션을 옮길 때는 내가 이런 세세한 것까지 다시 지시해야 한다는 걸 듣지 못했다.

이 말이 맞았다. 이런 건 사람이 외워 두는 게 아니라 **기록해 두는** 것이다. 그래서 이렇게 했다.

- **메모리 파일**: AI가 매 세션 시작에 읽는 파일에 작업 방식(설계 먼저, 천천히, 선택지), 개발 환경(Docker는 AI가 켠다), 블로그 흐름(네이버, 피클, 공개 저장소)을 적어 둔다.
- **`docs/PROGRESS.md`**: 진행 현황과 알려진 이슈. 새 세션이 가장 먼저 읽는다.
- **`CLAUDE.md`**: 프로젝트 규칙.
- **`docs/blog/notes.md`**: 글감 메모. 그때그때 적어 둔다.

그리고 새로운 규칙이 생길 때마다 그 자리에서 기록하기로 했다. 예를 들어 "커밋만 쌓아 놓지 말고 작은 단위마다 푸시할지 물어봐"라는 규칙도 말한 직후에 메모리에 적었다.

## 7. 챕터 1의 표를 다시 보며

챕터 1의 4절 표에는 "설명을 이해했는지, 실제로 돌려 보고 확인: 내가 한다"고 적었다. 지금 돌아보니 실제로는 AI도 브라우저로 화면을 열어 폰 폭에서 확인하는 일을 많이 했다. 폰 폭에서만 글자가 잘리는 문제는 그렇게 찾았다.
그래도 **무엇이 기준에 맞는지 판단하는 일**은 내가 했다. 확인하는 손은 둘이 나눠 쓰고, 합격 판정은 내가 한다고 고쳐 읽는 게 맞는 것 같다. [직접 확인]

## 8. 감수한 것

- 설계를 먼저 보여주고 선택지를 주고 멈추는 방식은 **느리다.** 하루에 끝낼 일이 이틀이 되기도 한다.
- 내 판단이 병목이다. 내가 모르는 걸 AI가 선택지로 줘도 고르는 건 나라서, 도메인을 모르는 영역에서는 틀릴 수 있다.
- 기록을 관리하는 일이 새로 생겼다. 메모리, 진행 문서, 글감 메모가 서로 어긋나지 않게 챙겨야 한다.
