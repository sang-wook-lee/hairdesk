## 1. 무엇을 만드나

미용사가 쓰는 예약·매출·고객 관리 앱을 만든다.

이런 앱이 없어서 만드는 건 아니다. 지금 미용사들이 쓰는 앱에도 예약(네이버나 카카오헤어 제휴), 매출 관리, 고객 메모 기능은 이미 다 있다. 내가 풀고 싶은 건 기능이 있느냐 없느냐가 아니라 **쓰기에 얼마나 편하냐**다.

범위는 이렇게 잡았다. 처음에는 1인 미용사만 대상으로 했다. 복잡도를 최대한 줄인 상태에서 설계를 시작하고 싶었기 때문이다. 지금은 미용사가 여러 명이어도 편하게 쓸 수 있도록 넓혀 가는 중이다.

왜 하필 미용사용 앱이냐면, 이 일이 나한테 남의 이야기가 아니라서다. 개발자로 일하던 회사를 그만두고 미용사 자격증을 따서 지금은 직접 일하고 있다. 현장에서 써 보니 지금 쓰는 예약 앱은 기능은 많은데 막상 쓰기에는 불편했다.

개발자로서의 나도 계속 키우고 싶었다. 그래서 공부도 할 겸 작은 서비스를 직접 만들되, 불편했던 점을 고쳐서 **실제로 경쟁력 있는 앱으로 출시**해 보고 싶다는 욕심이 생겼다.

## 2. 목표와 판단 기준

ADR 0001에는 목표를 세 가지로 적어 뒀다.

1. **백엔드 개발자 재취업용 포트폴리오**
2. **AI 도구 없이도 혼자 유지보수 가능할 것**
3. **가능하면 실제 출시**

기술을 고를 때의 판단 기준도 세 가지로 정했다.

1. **기존 경력과의 연속성**
2. **국내 백엔드 채용 시장**
3. **예약 도메인 적합성**

기준을 먼저 적어 두면 선택이 흔들릴 때 돌아갈 곳이 생긴다. 이후의 모든 선택을 "이 기준 중 뭐 때문인가"로 설명할 수 있다.

## 3. 내 출발점

- 경력: **Java + Spring Boot + Oracle**, SI 2년, 배달 플랫폼 백엔드 2년
- 그래서 기준 ①(경력 연속성)이 제일 먼저 나왔고, 새 언어(Kotlin)나 완전히 다른 생태계는 일부러 피했다.
- 반대로 **DB만은 익숙한 Oracle을 버렸다.** 이유는 아래 6~7절에 있다.

이 프로젝트로 보여주고 싶은 건 두 가지다.

- **현장의 불편에서 출발해서 문제를 푸는 힘.** 미용 현장에서 직접 겪은 불편이 요구사항의 출발점이다.
- **AI를 쓰되, 내가 이해하고 책임지는 개발 방식.** 4절에서 자세히 적는다.

## 4. 개발 원칙, 그리고 AI

프로젝트 규칙 파일(`CLAUDE.md`) 맨 위에 가장 중요한 원칙으로 이렇게 적었다.

> **개발자(오너)가 AI 없이도 이해하고 유지보수할 수 있어야 한다.**

이 원칙에서 작업 방식이 나왔다.

- 작게 나눠서 작업하고, 매 단계마다 "무엇을 왜 했는지" 설명을 받는다.
- 영리한 코드보다 읽히는 코드. 마법 같은 추상화는 쓰지 않는다.
- 기능 하나는 **설계 설명 → 구현 → 테스트 → 커밋**. 중요한 결정은 ADR로 남긴다.

이 프로젝트는 AI 코딩 도구(Claude Code)와 같이 만든다. 커밋 기록에도 공동 작성자로 남아 있다. 대신 **무엇을 어떻게 만들지는 내가 정한다.**

| 영역 | 누가 |
|---|---|
| 목표와 범위, 만드는 순서 | 내가 정한다 |
| 기술 선택과 트레이드오프의 최종 결정 | 내가 정한다 (AI는 선택지와 근거를 정리) |
| 작업을 쪼개는 단위 | 내가 정한다 |
| 되돌릴 수 없는 작업(예: 개발 DB 삭제)과 공개 범위 | 내가 승인한다 |
| 선택지·근거 정리, 구현 초안, 테스트 초안, 기록 | AI가 맡는다 |
| 설명을 이해했는지, 실제로 돌려 보고 확인 | 내가 한다 |

기술 선택에도 이 원칙이 들어가 있다. 아래 6절에 나오는 것처럼 **Kotlin을 고르지 않은 이유가 "AI 없이 유지보수하려면 가장 익숙한 언어가 유리하다"** 였다. AI가 쓰기 편한 언어가 아니라, 내가 끝까지 책임질 수 있는 언어를 골랐다는 뜻이다. 앞으로 챕터에서도 선택지가 나올 때마다 뭘 왜 골랐는지 같은 방식으로 적을 생각이다.

## 6. 고민했던 대안과 탈락 이유

| 대안 | 장점 | 채택하지 않은 이유 |
|---|---|---|
| Kotlin | 간결한 문법, null 안정성 | 학습 비용이 생기고, 국내 공고에서 필수인 곳은 아직 소수. **AI 없이 유지보수하려면 가장 익숙한 언어가 유리** |
| MyBatis | 기존 SI 경험과 일치, SQL 직접 제어 | 국내 서비스 회사 공고는 JPA가 사실상 기본. 상태가 바뀌는 예약·정액권 로직은 엔티티에 담는 편이 자연스러움. 단, JPA로 표현이 어색한 통계 쿼리는 억지로 풀지 않음 |
| Oracle | 가장 익숙함 | 무료판(XE)은 리소스 제한, 상용 라이선스·클라우드 비용이 개인 프로젝트에 부담, 채용 시장이 SI·금융 쪽에 치우침 |
| MySQL | 국내 서비스 회사에서 가장 많이 씀 | PostgreSQL의 도메인 적합성이 더 크다고 판단. SQL·JPA 경험은 DB 간 대부분 이전 가능 |
| Maven | 널리 쓰이는 빌드 도구 | 국내 서비스 회사는 Gradle이 더 일반적. Kotlin DSL 대신 Groovy DSL을 쓴 이유는 Kotlin 문법 없이 읽을 수 있고 참고 자료가 가장 많아서 |

이 중에서 제일 팽팽했던 건 **MySQL과 PostgreSQL**이었다. Oracle은 비용이랑 채용 시장 문제로 일찍 빠졌는데, MySQL은 국내 서비스 회사에서 가장 많이 쓰고 공고 수도 더 많다는 확실한 장점이 있었다. 취업이 목표라면 MySQL이 더 안전한 선택일 수도 있었다.

결국 갈라 놓은 건 7절의 **예약 겹침 제약**이다. 이 서비스에서 제일 중요한 규칙인 "같은 담당자의 시간은 겹칠 수 없다"를 코드가 아니라 DB가 보장해 주는 쪽은 PostgreSQL이었다. SQL이랑 JPA 경험은 DB가 달라도 대부분 이어지니까, 공고 수의 이점보다 이쪽이 크다고 판단했다.

## 7. PostgreSQL을 고른 결정적 이유

가장 익숙한 Oracle을 두고 PostgreSQL을 고른 이유는 네 가지다.

1. **이중 예약 방지를 DB 제약조건으로 강제할 수 있다.** 범위 타입(`tstzrange`)과 `EXCLUDE USING gist` 제약으로 "같은 디자이너의 예약 시간은 겹칠 수 없다"를 DB가 보장한다. 동시 요청이 들어와도 애플리케이션 락 없이 막힌다.
2. **DDL도 트랜잭션 안에서 실행된다.** Flyway 마이그레이션이 중간에 실패하면 깔끔하게 롤백된다. (MySQL은 DDL을 실행하면 암묵적으로 커밋된다.)
3. **Oracle과 개념이 가깝다.** 시퀀스, PL/pgSQL, MVCC 같은 것들이라 경력이 이어진다.
4. 무료이고, 클라우드 무료 티어 선택지가 많다.

핵심은 1번이다. "저장하기 전에 겹치는 예약이 있는지 조회하고, 없으면 저장"하는 방식은 거의 동시에 들어온 두 요청이 **둘 다 조회를 통과**할 수 있다. 그걸 애플리케이션 코드가 아니라 DB가 막게 하고 싶었다. ADR을 쓰던 시점의 구상은 이런 모양이었다.

```sql
-- 구상 (ADR 작성 시점). 같은 디자이너의 예약 구간이 겹치면(&&) DB가 거부한다.
EXCLUDE USING gist (designer_id WITH =, tstzrange(start_at, end_at) WITH &&)
```

`designer_id WITH =`처럼 일반 컬럼에 `=`를 쓰려면 `btree_gist` 확장이 필요하다. 그래서 첫날 만든 V1 마이그레이션이 바로 이 확장을 켠다. 그 제약을 실제로 어떻게 만들고 동시 요청으로 검증했는지는 **챕터 3**에서 이어진다.

> 이 결정의 대가도 ADR에 적어 뒀다. 면접에서 "동시성 문제를 DB 제약으로 해결했다"고 말할 수 있는 구체적인 사례가 생기는 대신, PostgreSQL 고유 기능에 묶인다. **이식성보다 데이터 무결성을 우선한다**고 정했다.

| 설정 | 이유 |
|---|---|
| `postgres:17` 이미지 버전 고정 | `latest`는 언젠가 메이저 버전이 바뀌어서 갑자기 깨질 수 있다. 테스트(Testcontainers)도 같은 버전을 쓴다 |

| 첫 테스트부터 Testcontainers | ADR 0001의 "실제 PostgreSQL로 통합 테스트" 결정을 첫 테스트부터 적용. (참고: H2 같은 대체 DB로는 `EXCLUDE` 같은 PostgreSQL 고유 기능을 검증할 수 없다) |

## 9. 감수한 것

- PostgreSQL 고유 기능(`EXCLUDE` 등)을 쓰면 다른 DB로 옮기기 어려워진다. 이식성보다 무결성을 택했다.
- 로컬 개발에 Docker가 필요하다.
- Kotlin을 안 쓰면서 문법의 간결함은 포기했다. 대신 내가 끝까지 읽고 고칠 수 있는 코드를 얻는다.

| 통계 쿼리는 "QueryDSL 또는 네이티브 SQL" | QueryDSL은 도입하지 않았다. 대부분 JPQL 생성자 표현식으로 풀고, **서울 날짜별 묶음만 네이티브 SQL**을 썼다 | 챕터 5 |
| 예약 제약은 "같은 디자이너(=) + 시간 겹침(&&)" | 처음에는 1인 기준이라 **시간 겹침만** 막았다. 이후 직원(담당자)을 도입하면서 `staff_id WITH =`가 추가되어, 첫날 구상한 모양대로 **같은 담당자의 예약만** 겹치지 않게 바뀌었다 | 챕터 3 |
| 클라이언트는 "Flutter (백엔드 이후)" | 백엔드 핵심(9/30) 완료 약 3주 뒤인 10/23에 Flutter 시작 | 챕터 6 |
| Spring Boot는 "생성 시점의 최신 안정 버전" | 4.1.1 | 이 글 8절 |
| "AI 없이도 유지보수 가능할 것" | 백엔드(Java, Spring, DB)는 AI 없이 코드를 열어도 따라갈 수 있다고 느낀다. 아직 어려운 쪽은 **앱(Flutter)** 이다. | 전체 |
