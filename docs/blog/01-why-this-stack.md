## 1. 무엇을 만드나

혼자 일하는 미용사는 예약은 메신저로, 고객 메모는 수첩으로, 매출은 엑셀로 따로 관리하는 경우가 많습니다. 이 세 가지를 한 앱에서 다루는 서비스를 만듭니다.

> **[직접 채우기]** 왜 하필 미용사용 예약 앱을 골랐는지 한두 문장. (주변에서 본 불편, 도메인이 단순하면서도 동시성 같은 어려운 문제가 있어서 등, 본인의 실제 이유)

## 2. 목표와 판단 기준

ADR 0001은 목표를 세 가지로 적어 두었습니다.

1. **백엔드 개발자 재취업용 포트폴리오**
2. **AI 도구 없이도 혼자 유지보수 가능할 것**
3. **가능하면 실제 출시**

그리고 기술을 고를 때의 판단 기준도 세 가지로 정했습니다.

1. **기존 경력과의 연속성**
2. **국내 백엔드 채용 시장**
3. **예약 도메인 적합성**

기준을 먼저 적어 두면 선택이 흔들릴 때 돌아갈 곳이 생깁니다. 이후의 모든 선택이 "이 기준 중 무엇 때문인가"로 설명됩니다.

## 3. 내 출발점

- 경력: **Java + Spring Boot + Oracle**, SI 2년, 배달 플랫폼 백엔드 2년
- 그래서 기준 ①(경력 연속성)이 가장 먼저 나왔고, 새 언어(Kotlin)나 완전히 다른 생태계는 일부러 피했습니다.
- 반대로 **DB만은 익숙한 Oracle을 버렸는데**, 이유는 아래 6~7절에 있습니다.

> **[직접 채우기]** 이 프로젝트를 통해 보여주고 싶은 것(예: SI·서비스 회사 경험 위에서 동시성·테스트·문서화까지 갖춘 개발 방식).

## 4. 개발 원칙, 그리고 AI

프로젝트 규칙 파일(`CLAUDE.md`)의 맨 위에 가장 중요한 원칙으로 이렇게 적었습니다.

> **개발자(오너)가 AI 없이도 이해하고 유지보수할 수 있어야 한다.**

이 원칙에서 작업 방식이 나옵니다.

- 작게 나눠서 작업하고, 매 단계마다 "무엇을 왜 했는지" 설명을 받는다.
- 영리한 코드보다 읽히는 코드. 마법 같은 추상화는 쓰지 않는다.
- 기능 하나는 **설계 설명 → 구현 → 테스트 → 커밋**. 중요한 결정은 ADR로 남긴다.

이 프로젝트는 AI 코딩 도구(Claude Code)와 함께 만듭니다. 커밋 기록에도 공동 작성자로 남아 있습니다. 대신 **무엇을 어떻게 만들지는 제가 결정**합니다.

| 영역 | 누가 |
|---|---|
| 목표와 범위, 만드는 순서 | 내가 정한다 |
| 기술 선택과 트레이드오프의 최종 결정 | 내가 정한다 (AI는 선택지와 근거를 정리) |
| 작업을 쪼개는 단위 | 내가 정한다 |
| 되돌릴 수 없는 작업(예: 개발 DB 삭제)과 공개 범위 | 내가 승인한다 |
| 선택지·근거 정리, 구현 초안, 테스트 초안, 기록 | AI가 맡는다 |
| 설명을 이해했는지, 실제로 돌려 보고 확인 | 내가 한다 |

기술 선택 자체에도 이 원칙이 들어 있습니다. 아래 6절에서 보듯 **Kotlin을 고르지 않은 이유가 "AI 없이 유지보수하려면 가장 익숙한 언어가 유리하다"** 였습니다. AI가 쓰기 편한 언어가 아니라, 제가 끝까지 책임질 수 있는 언어를 골랐다는 뜻입니다. 이후 챕터에서도 선택지가 나올 때마다 어떤 것을 왜 골랐는지 같은 방식으로 적습니다.

> **[직접 확인]** 위 역할 표가 실제 작업 감각과 맞는지, 빼거나 보탤 항목이 있는지 확인해 주세요. 예를 들어 첫날 스택을 정할 때 실제로 누가 어떤 선택지를 냈고 무엇을 직접 골랐는지 기억나는 사례가 있으면 여기에 한 줄 넣으면 가장 설득력 있습니다.

## 6. 고민했던 대안과 탈락 이유

| 대안 | 장점 | 채택하지 않은 이유 |
|---|---|---|
| Kotlin | 간결한 문법, null 안정성 | 학습 비용이 생기고, 국내 공고에서 필수인 곳은 아직 소수. **AI 없이 유지보수하려면 가장 익숙한 언어가 유리** |
| MyBatis | 기존 SI 경험과 일치, SQL 직접 제어 | 국내 서비스 회사 공고는 JPA가 사실상 기본. 상태가 바뀌는 예약·정액권 로직은 엔티티에 담는 편이 자연스러움. 단, JPA로 표현이 어색한 통계 쿼리는 억지로 풀지 않음 |
| Oracle | 가장 익숙함 | 무료판(XE)은 리소스 제한, 상용 라이선스·클라우드 비용이 개인 프로젝트에 부담, 채용 시장이 SI·금융 쪽에 치우침 |
| MySQL | 국내 서비스 회사에서 가장 많이 씀 | PostgreSQL의 도메인 적합성이 더 크다고 판단. SQL·JPA 경험은 DB 간 대부분 이전 가능 |
| Maven | 널리 쓰이는 빌드 도구 | 국내 서비스 회사는 Gradle이 더 일반적. Kotlin DSL 대신 Groovy DSL을 쓴 이유는 Kotlin 문법 없이 읽을 수 있고 참고 자료가 가장 많아서 |

> **[직접 채우기]** 이 중 가장 마지막까지 고민했던 것은 무엇이었는지(예: MySQL vs PostgreSQL), 그때 무엇이 결정을 갈랐는지.

## 7. PostgreSQL을 고른 결정적 이유

가장 익숙한 Oracle을 두고 PostgreSQL을 고른 이유는 네 가지였습니다.

1. **이중 예약 방지를 DB 제약조건으로 강제할 수 있다.** 범위 타입(`tstzrange`)과 `EXCLUDE USING gist` 제약으로 "같은 디자이너의 예약 시간은 겹칠 수 없다"를 DB가 보장합니다. 동시 요청이 들어와도 애플리케이션 락 없이 막힙니다.
2. **DDL도 트랜잭션 안에서 실행된다.** Flyway 마이그레이션이 중간에 실패하면 깔끔하게 롤백됩니다. (MySQL은 DDL 실행 시 암묵적 커밋)
3. **Oracle과 개념이 가깝다.** 시퀀스, PL/pgSQL, MVCC 등이라 경력이 이어집니다.
4. 무료이고, 클라우드 무료 티어 선택지가 많습니다.

핵심은 1번입니다. "저장 전에 겹치는 예약이 있는지 조회하고, 없으면 저장"하는 방식은 거의 동시에 들어온 두 요청이 **둘 다 조회를 통과**할 수 있습니다. 그걸 애플리케이션 코드가 아니라 DB가 막게 하고 싶었습니다. ADR을 쓰던 시점의 구상은 이런 모양이었습니다.

```sql
-- 구상 (ADR 작성 시점). 같은 디자이너의 예약 구간이 겹치면(&&) DB가 거부한다.
EXCLUDE USING gist (designer_id WITH =, tstzrange(start_at, end_at) WITH &&)
```

`designer_id WITH =` 처럼 일반 컬럼에 `=`를 쓰려면 `btree_gist` 확장이 필요해서, 첫날 만든 V1 마이그레이션이 바로 이 확장을 켭니다. 그 제약을 실제로 어떻게 만들고 동시 요청으로 검증했는지는 **챕터 3**에서 이어집니다.

> 이 결정의 대가는 ADR에도 적어 두었습니다. 면접에서 "동시성 문제를 DB 제약으로 해결했다"고 말할 수 있는 구체적인 사례가 생기는 대신, PostgreSQL 고유 기능에 묶입니다. **이식성보다 데이터 무결성을 우선한다**고 정했습니다.

| 설정 | 이유 |
|---|---|
| `postgres:17` 이미지 버전 고정 | `latest`는 언젠가 메이저 버전이 바뀌어 갑자기 깨질 수 있다. 테스트(Testcontainers)도 같은 버전을 쓴다 |
| 로컬 DB 포트 고정(5432) | DBeaver 같은 DB 툴로 직접 붙어서 데이터를 볼 수 있게 |

| `ddl-auto: validate` | 스키마는 Flyway만 바꾼다. Hibernate는 엔티티와 테이블이 맞는지 검사만 한다 |
| 첫 테스트부터 Testcontainers | ADR 0001의 "실제 PostgreSQL로 통합 테스트" 결정을 첫 테스트부터 적용. (참고: H2 같은 대체 DB로는 `EXCLUDE` 같은 PostgreSQL 고유 기능을 검증할 수 없다) |

## 9. 감수한 것

- PostgreSQL 고유 기능(`EXCLUDE` 등)을 쓰면 다른 DB로 옮기기 어려워집니다. 이식성보다 무결성을 택했습니다.
- 로컬 개발에 Docker가 필요합니다.
- Kotlin을 쓰지 않으면서 문법의 간결함은 포기했습니다. 대신 제가 끝까지 읽고 고칠 수 있는 코드를 얻습니다.
