테스트가 한 번에 초록색으로 통과하면 기분이 좋다. 그런데 그게 "테스트가 맞다"는 뜻일까? 이번에는 오히려 처음부터 통과한 테스트를 일부러 망가뜨려 보기로 했다.

---

## 한 장 요약 (복기용)

| 항목 | 내용 |
|---|---|
| 방법 | 통과한 테스트마다 **코드를 일부러 망가뜨리고**(변이), 테스트가 실패하는지 본다 |
| 직원 기능에서 | 검사 코드를 지워도 통과하는 테스트 둘을 찾아 고쳤다 |
| 고객 요약에서 | 쿼리 7가지, 서비스 8가지를 망가뜨려 전부 잡힘을 확인했다 |
| 실수 | 변경 스크립트의 줄바꿈 오류로 첫 시도가 전부 무효였다 |
| 덤 | 전체 테스트에서 요일에 따라 실패하는 오래된 테스트를 발견해 요일 7개로 증명하고 고쳤다 |

---

## 1. 왜 통과한 테스트를 의심하나

테스트가 실패하면 뭔가 틀렸다는 걸 바로 안다. 위험한 건 **통과하는데 아무것도 검사하지 않는 테스트**다. 코드가 틀려도 계속 초록색이라서 안심하게 만든다.
그래서 규칙을 하나 정했다. 테스트가 처음부터 통과하면, 검사 대상 코드를 일부러 망가뜨려 보고 **그 테스트가 정말로 실패하는지** 확인한다. 실패하지 않으면 테스트가 틀린 것이다.

## 2. 직원 기능에서 잡은 것

두 가지가 걸렸다.

- **저장 순서를 지키는 코드를 지워도 통과했다.** 주인을 바꿀 때 기존 표시를 끄고 새 표시를 켜는 순서가 DB 제약 때문에 중요했는데, 그 순서를 보장하는 코드를 지워도 테스트는 초록색이었다. 같은 트랜잭션 안에서는 메모리에 올라온 객체를 그대로 읽어서 DB가 실제로 어땠는지 보지 못했기 때문이다. 테스트 안에서 메모리를 비우고 DB에서 다시 읽도록 고쳤다. (이 주인 변경 기능은 이후 통째로 지워졌지만, 교훈은 남았다. 챕터 11 참고)
- **상태 코드만 보는 테스트는 다른 경로가 같은 코드를 내도 모른다.** "담당자 없이 예약하면 400"을 확인하는 테스트에서, 담당자 필수 검사를 지워도 400이 나왔다. 요청 형식을 검사하는 다른 경로가 같은 400을 내고 있었다. 상태 코드가 아니라 **오류 메시지에 `staffId`가 들어 있는지**까지 확인하도록 고쳤다.

## 3. 고객 요약에서 한 변이 확인

고객 요약 API(챕터 13)에서는 이 확인을 체계적으로 했다. 저장소 쿼리 3개에 대해 쿼리를 7가지로 망가뜨렸다.

| 망가뜨린 곳 | 실패한 테스트 |
|---|---|
| 합계를 받은 금액 대신 정가로 | 횟수·합계·날짜 테스트 |
| 첫·최근 방문일을 서로 바꿈 | 같은 테스트 |
| 매출 집계에서 고객 조건을 지움 | 다른 고객 매출이 안 섞임 |
| 최근 결제를 결제 시각이 아니라 저장 순서로 | 최근 결제는 결제 시각 기준 |
| 담당자를 함께 가져오는 설정을 지움 | 담당자도 함께 가져옴 |
| 예약 집계에서 고객 조건을 지움 | 다른 고객 예약은 안 셈 |
| 같은 시각이면 번호가 작은 쪽을 고름 | 번호가 큰 쪽이 최근 |

서비스에서는 8가지를 망가뜨렸다. 합계가 null일 때 0으로 바꾸는 처리, 평균 반올림, 방문이 0일 때 평균 null, 취소·노쇼 칸 바꿔치기, 예약 수 계산, 없는 고객 404, 서울 시간 변환, 최근 결제가 없을 때의 null 처리다. 8가지 모두 의도한 테스트가 실패했다.

## 4. 내 실수: 첫 시도는 아무것도 망가뜨리지 못했다

이 확인에도 실수가 있었다. 변경 스크립트를 고치다가 줄바꿈을 잘못 넣어서 스크립트가 아예 실행되지 않았다. 7번 모두 "변경 실패"라는 메시지만 나왔고, **쿼리는 한 군데도 망가지지 않은 채**였다. 이 결과로는 아무것도 확인한 게 아니었다.
오류가 눈에 보여서 바로 알았지만, 출력을 대충 봤다면 "문제 없음"으로 읽을 뻔했다. 스크립트를 처음부터 다시 쓰고, 이번에는 변경이 실제로 파일에 적용됐는지를 매번 확인한 뒤 돌렸다.

"테스트가 통과했다"만큼 **"내가 의도한 걸 실제로 했는가"** 도 확인해야 한다. 변이 확인도 결국 코드니까 틀릴 수 있다.

## 5. 덤: 요일에 따라 실패하는 테스트

고객 요약을 끝내고 백엔드 전체 테스트를 돌렸더니, 내 변경과 상관없는 테스트 하나가 실패했다. 샘플 데이터를 넣고 "최근 14일에 신규 고객이 있어야 한다"를 확인하는 테스트였다.

먼저 **내 탓인지 아닌지**부터 가렸다. 내 변경을 모두 치우고 같은 테스트를 돌렸더니 똑같이 실패했다. 원래 있던 문제였다. 11월 21일(토요일)에는 통과했고 24일(화요일)에는 실패했으니 날짜가 원인일 것 같았다.

그래도 추측으로 고치지 않았다. 샘플 데이터 생성기의 "오늘"을 하루씩 바꿔 가며 7일을 돌려 봤다.

| 오늘의 요일 | 14일 기간 신규 고객 | 21일 기간 신규 고객 |
|---|---|---|
| 화·수·목 | **0명** (테스트 실패) | 4명 |
| 금·토·일 | 2명 | 4명 |
| 월 | 1명 | 4명 |

원인은 생성기가 일요일을 건너뛰면서, 오늘이 무슨 요일이냐에 따라 난수로 뽑히는 고객의 순서가 달라진다는 점이었다. 신규 고객은 21일 전부터 등장하게 설계했는데 테스트는 14일만 봤다. 기간을 21일로 맞추자 7일 모두 신규 4명, 재방문 8명이 나왔다. 고친 뒤에도 생성기가 신규 고객을 아예 안 만들게 망가뜨려서, 테스트가 여전히 실패하는 것을 확인했다.

## 6. 감수한 것

- 통과한 테스트마다 망가뜨려 보면 시간이 두세 배 걸린다. 그래서 모든 테스트가 아니라 **계산·조건·쿼리처럼 틀리기 쉬운 곳**에 집중했다.
- 변이는 내가 떠올린 것만 시험한다. 못 떠올린 틀림은 그대로 둔다.

## 복기 노트

| 처음 생각 | 실제 결과 |
|---|---|
| 테스트가 통과하면 검사가 되는 것 | 검사 코드를 지워도 통과하는 테스트가 있었다 |
| 상태 코드만 확인해도 충분 | 다른 경로가 같은 코드를 내서 구분이 안 됨 → 메시지까지 확인 |
| 변이 확인은 한 번에 맞게 돌린다 | 스크립트 오류로 첫 시도가 무효(변경이 하나도 적용되지 않음). 적용됐는지부터 확인 |
| 날짜에 따라 달라지는 테스트는 눈에 띈다 | 3일 전엔 통과하던 테스트가 요일이 바뀌자 실패. 요일 7개로 증명 |

### 이 글을 다시 볼 때 던질 질문

1. 변이 확인을 계속 하고 있나, 아니면 귀찮아서 건너뛰고 있나?
2. 변이를 떠올리기 어려운 코드(화면, 시간대, 동시성)에서는 무엇으로 대신하고 있나?
3. 오늘 날짜를 쓰는 다른 테스트가 또 있지는 않은가?
