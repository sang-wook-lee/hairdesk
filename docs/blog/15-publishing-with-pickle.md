개발 일지를 쓰는 것과 그걸 블로그에 올리는 것은 다른 일이다. 글은 PC에서 마크다운으로 쓰는데, 네이버 블로그는 마크다운을 모른다. 이 둘 사이를 어떻게 이을까?

---

## 한 장 요약 (복기용)

| 항목 | 내용 |
|---|---|
| 흐름 | PC에서 Claude Code로 글 작성 → 내가 검토 → GitHub에 푸시 → 폰의 피클이 받아서 네이버에 올림 |
| 처음 생각 | "네이버는 자동 게시가 안 된다" (글쓰기 API가 종료돼서) |
| 실제 | 피클이 블로그 글쓰기 화면을 직접 조작해 올렸다. API 없이도 가능했다 |
| 변환 결과 | 제목·목록·구분선·굵게는 잘 됨, 표는 되지만 격자선이 흐림, 백틱은 사라짐 |
| 올리기 전에 한 일 | 공개 저장소라서 비밀값을 커밋 기록 전체에서 검사했다 |
| 글 쓰는 방식 | 말투가 "AI티가 난다"는 지적으로 일기체로 다시 썼다 |

## 1. 흐름을 이렇게 만들었다

블로그는 네이버 블로그다. 쓰고 있는 AI 에이전트 앱 **피클**은 폰에서만 쓸 수 있고 PC에서는 못 쓴다. 그래서 역할을 나눴다.

1. **PC에서** Claude Code가 `docs/blog/`에 마크다운 글을 쓴다. 근거는 ADR, 커밋 기록, 코드다.
2. **내가** 읽고, 직접 채울 곳을 채우고, 사실을 확인한다.
3. **GitHub에 푸시**한다. (공개 저장소라서 푸시는 내가 허락할 때만 한다)
4. **폰의 피클**이 GitHub에서 글을 받아 네이버 블로그에 올린다.

PC 키보드로 피클을 쓰고 싶으면 윈도우의 "휴대폰과 연결"이나 삼성 플로우 같은 화면 미러링으로 폰 앱을 띄우는 방법이 있다. 이 부분은 글쓰기와 상관없는 편의 문제다.

글의 원본이 저장소에 남는다는 점이 이 구조의 장점이다. 피클이 바뀌거나 사라져도 기록은 남는다. 블로그에 올라가는 글의 내용은 이 프로젝트를 아는 쪽(나와 AI)이 책임지고, 피클에는 올리는 반복 작업만 맡긴다.

## 2. "자동 게시는 불가능"이라고 적었다가 고쳤다

처음에 블로그 README에는 "네이버는 자동 게시가 불가능하다"고 적었다. 네이버의 글쓰기 API가 2020년에 종료됐다는 보도를 근거로 한 말이었다. 그래서 직접 올려야 한다고 안내했다.

그런데 피클은 API를 쓰지 않았다. 폰에서 **블로그 글쓰기 화면을 사람처럼 조작**해서 올렸다. "API가 없으니 불가능"은 틀린 추론이었다. 시험 발행을 해 보고 README를 고쳤다.
결론: 문서에 "불가능"이라고 쓰기 전에, 가능한지 한 번 해 보는 게 낫다.

## 3. 시험 발행 결과

챕터 1을 **비공개**로 올려 봤다. 피클이 직접 정리해 준 결과다.

| 마크다운 | 네이버에서 |
|---|---|
| 제목·목록·구분선·굵게 | 잘 변환됨 |
| 인용구 | 변환되지만 가운데 정렬이 기본 |
| 표 | 들어가지만 안쪽 격자선이 없고 바깥 테두리만 흐림. 에디터에서 표마다 테두리 색을 넣을 수 있음 |
| 코드 블록 | 붙여넣으면 일반 문단이 됨. 피클이 에디터의 "소스코드 추가" 기능으로 직접 넣어서 SQL 하이라이팅까지 정상 |
| 인라인 코드(백틱) | 전용 서식이 없어서 백틱이 빠지고 일반 글자로 나옴 |

그래서 글을 쓸 때 이렇게 하기로 했다.

- 중요한 용어는 백틱 대신 **굵게**로 강조한다. 서식이 살아남는다.
- 코드는 짧게 쓴다.
- 맨 위 메모 주석(`<!-- -->`)은 발행 전에 지운다.
- 피클이 자동으로 붙이는 태그(예: `#첫글`)는 발행 전에 확인한다.

피클은 올리는 중에 이런 것도 알려 줬다. 프롤로그가 11월 18일 기준이라 숫자(ADR, 커밋, API, 테스트 수)와 예약 제약 SQL이 최신이 아니라는 것이다. 루트 README의 숫자도 낡았다고 했다. 공개 저장소라서 직접 고치거나 푸시하지는 않고, 말만 하겠다고 했다. 그 말대로 고치는 건 내 쪽에서 했다.

> **[직접 채우기]** 피클을 써 본 경험 한두 줄. (처음 써 보니 어땠는지, 기대와 달랐던 점, 블로그 계정 로그인을 에이전트에 맡기는 게 어땠는지 등)

## 4. 올리기 전에 한 일: 비밀값 검사

저장소는 공개다. 그래서 푸시하면 코드와 **커밋 기록 전체**가 누구에게나 보인다. 한 번 올라가면 지워도 기록에 남는다. 올리기 전에 검사했다.

- 비밀번호·키·토큰 같은 패턴을 커밋 기록 전체에서 찾았다. 환경 파일과 키 파일은 한 번도 커밋된 적이 없었다.
- 걸린 것은 개발용 DB 계정(로컬 전용 값)뿐이었다. 위험은 낮다고 판단했다.
- 집 와이파이의 사설 IP 주소가 코드 주석과 테스트에 예시로 들어 있었다. 외부에서 접근할 수 없는 주소지만 공유기 대역이 드러난다.
- 커밋 작성자 이메일이 기록에 남아 있었다. 공개 저장소에서는 누구나 볼 수 있다. 연락처로 쓸 수 있다고 보고 그대로 두기로 했다.

판단은 내가 했고, 푸시는 그 뒤에 했다. **되돌릴 수 없는 일은 먼저 점검하고, 허락받고 한다.**

## 5. 글을 쓰는 방식도 고쳤다

처음 초안은 "~합니다" 체의 보고서 같은 글이었다. 읽어 보고 "AI티가 너무 난다"고 말했다. 그래서 일기장처럼 "나/내가 ~다"로 다시 썼다. 같은 내용도 말투 하나로 내 글처럼 읽히는지가 갈렸다.

글의 내용도 사실과 맞게 고쳤다. 처음엔 "혼자 일하는 미용사를 위한 앱"이라고 썼는데, 지금은 직원이 여러 명이어도 쓰게 만들고 있다. 비슷한 앱이 이미 있다는 점, 문제는 기능의 유무가 아니라 쓰기 편한 정도라는 점도 반영했다.

## 6. 감수한 것

- 피클은 폰에서만 쓸 수 있어서, 올리는 순간만은 PC에서 못 한다.
- 표 격자선, 인용구 정렬 같은 서식은 네이버 에디터에서 손으로 고쳐야 한다.
- 올리는 일을 에이전트에 맡기는 만큼, 올리기 전에 내가 직접 읽어 보는 단계가 꼭 필요하다.
- 이미지가 포함된 글의 올리기는 아직 시험하지 않았다.
